《土豆修仙》
战斗与伤害系统开发规则 V1.0
用途：Claude Code 开发基线
本文定义《土豆修仙》当前版本的角色属性、伤害计算、战斗事件、暴击、BD增伤、攻击频率以及DPS的底层规则。
本文是开发规则，不是玩法策划案。
Claude Code 实现时，应优先遵守本文的结构与边界，不应自行增加新的伤害乘区、防御体系或复杂计算规则。
________________________________________
一、项目当前战斗系统定位
《土豆修仙》当前采用：
修仙题材 + 增量/放置战斗 + 简单清晰的数值成长 + BD组合
首版战斗系统追求：
•	公式简单
•	规则统一
•	数值容易调
•	玩家容易理解
•	BD有明显组合价值
•	后续能够扩展更多技能和战斗事件
不追求：
•	复杂防御公式
•	大量属性相克
•	复杂抗性系统
•	多套互相独立的伤害公式
•	为了“专业”而增加大量计算层
________________________________________
二、首版明确不实现的内容
首版暂时不建立以下体系：
DEF
Armor
Magic Resist
Damage Reduction
Element Resistance
Block
Parry
Penetration
Armor Penetration
Resistance Penetration
也就是说：
当前版本主要通过“攻击者伤害能力”与“敌人HP”建立核心数值轴。
敌人主要通过：
HP
承担耐久成长。
攻击者主要通过：
AttackPower
伤害倍率
暴击
通用增伤
BD增伤
其他战斗机制
承担输出成长。
不要因为以后可能需要防御系统，就提前把这些系统写进当前DamageSystem。
________________________________________
三、整体战斗计算架构
完整流程：
角色最终属性
      ↓
Attack Event
      ↓
DMG1：生成原始伤害
      ↓
DMG2：战斗事件瀑布
      │
      ├─ 目标确定
      ├─ 命中/闪避等判定
      ├─ 暴击判定
      ├─ 状态与触发条件
      ├─ 生成 Damage Event
      │
      └─ 调用 DMG3
             ↓
      DMG3：最终伤害倍率
             ↓
      Final Damage
             ↓
      实际扣除目标HP
             ↓
      后续战斗事件
             ↓
      OnHit / OnCrit / OnKill / ...
             ↓
      可能产生新的Attack Event
             ↓
      重新进入战斗流程
核心思想：
DMG1负责“产生多少基础伤害”。
DMG2负责“这次攻击在战斗中发生了什么”。
DMG3负责“这一笔实际伤害最终放大多少”。
________________________________________
四、所有伤害行为统一公式
这是本项目最重要的开发原则之一。
无论伤害来源是：
•	普攻
•	技能
•	额外攻击
•	触发攻击
•	状态伤害
•	BD产生的攻击
•	其他未来新增伤害行为
原则上都必须进入统一的：
Damage Event
并经过统一的：
DMG1
→ DMG2
→ DMG3
流程。
不能给不同技能单独写一套伤害计算公式。
________________________________________
五、Skill数据统一管理
普攻和技能不要使用两套完全不同的伤害系统。
统一使用：
Skill
数据定义。
可以通过Skill数据区分：
Basic Attack
Active Skill
Triggered Skill
Other Skill
但它们最终都应该生成标准的：
Attack Event
然后进入统一战斗流程。
________________________________________
六、攻击频率与伤害计算分离
伤害大小与攻击频率是两个不同维度。
Attack Speed
负责：
普攻多久攻击一次。
CDR
负责：
技能多久可以再次释放。
不要把Attack Speed或者CDR直接塞进伤害倍率。
例如：
一次普攻伤害 = 100
攻击频率 = 2次/秒
则：
DPS = 100 × 2 = 200
攻击速度改变的是：
Hits Per Second
而不是：
Damage Multiplier
________________________________________
七、DMG1：原始伤害生成
7.1 DMG1定义
DMG1回答：
“如果这一攻击正常造成伤害，在任何最终放大之前，它的基础伤害是多少？”
当前版本DMG1采用：
DMG1
=
AttackPower
×
SkillRate
+
SkillFlat
其中：
AttackPower
是攻击者当前最终面板攻击力。
SkillRate
是当前Skill自身的伤害倍率。
SkillFlat
是该Skill提供的固定伤害。
________________________________________
八、DMG1示例
角色：
AttackPower = 100
技能：
SkillRate = 2.0
SkillFlat = 20
则：
DMG1
=
100 × 2.0 + 20
=
220
此时：
220
只是：
原始伤害值。
还没有进行：
•	暴击
•	通用增伤
•	BD增伤
•	易伤
•	其他最终伤害放大
________________________________________
九、SkillRate的职责
SkillRate是：
技能自身的伤害倍率。
例如：
普攻 = 1.0
技能A = 1.5
技能B = 3.0
SkillRate直接参与DMG1。
不要把SkillRate放入DMG3。
因为：
技能本身有多强，是技能定义；这个技能因为BD/状态/暴击被放大多少，是DMG3。
两者必须分离。
________________________________________
十、DMG2：Combat Event Resolution
10.1 DMG2不是“技能伤害计算层”
DMG2正式定义为：
Combat Event Resolution
战斗事件瀑布结算层
它负责解决：
“一次攻击发生之后，战斗系统依次发生了什么？”
DMG2不是简单计算一个倍率。
________________________________________
十一、DMG2的核心职责
DMG2负责处理：
Attack Event
Target Resolution
Hit Resolution
Critical Resolution
Damage Event
Damage Application
OnHit
OnCrit
OnDamage
Status
Resilience / Stagger等战斗事件
Death
OnKill
Chain Event
具体功能可以随着项目需要增加，但必须遵守：
事件发生顺序明确。
________________________________________
十二、基础战斗事件瀑布
当前建议使用以下基础顺序：
Attack Event
    ↓
Target Resolution
    ↓
Hit Resolution
    ↓
Critical Resolution
    ↓
Damage Event
    ↓
DMG3
    ↓
Apply Damage
    ↓
OnDamage / OnHit / OnCrit
    ↓
状态处理
    ↓
死亡判定
    ↓
OnKill
    ↓
Chain / Trigger Event
不是每次攻击都会经过全部节点。
例如攻击没有命中：
Attack
 ↓
Target
 ↓
Hit Check
 ↓
Miss
 ↓
结束
而如果目标死亡：
Damage
 ↓
Apply Damage
 ↓
HP <= 0
 ↓
Death
 ↓
OnKill
 ↓
产生新的Attack Event
________________________________________
十三、命中/闪避
DMG2负责处理命中相关的战斗事件。
例如：
Attack Event
    ↓
Hit Check
    ↓
Hit
或者：
Attack Event
    ↓
Hit Check
    ↓
Miss
    ↓
结束
当前版本不建立：
命中属性
闪避属性
格挡
招架
等复杂数值体系。
如果当前技能/战斗事件需要命中失败表现，可以由事件规则处理。
不要因为存在Hit Resolution，就自动扩展成完整的Accuracy/Evasion属性系统。
________________________________________
十四、暴击判定属于DMG2
这一点必须明确：
暴击“是否发生”属于DMG2。
例如：
Attack
 ↓
Hit
 ↓
Crit Check
 ↓
Critical = YES
DMG2记录：
is_critical = true
然后进入DMG3。
________________________________________
十五、暴击伤害倍率属于DMG3
DMG2只负责：
这一次攻击是不是暴击。
DMG3负责：
如果是暴击，这一次伤害应该获得多少暴击倍率。
因此：
DMG2
    ↓
is_critical = true
    ↓
DMG3
    ↓
CriticalMultiplier
这两个职责不能混淆。
________________________________________
十六、DMG3：最终伤害倍率
DMG3负责：
对已经确定要造成的这一笔伤害，计算最终倍率。
当前DMG3由四个概念组成：
Generic
Critical
Build
Vulnerability
即：
DMG3
=
GenericMultiplier
×
CriticalMultiplier
×
BuildMultiplier
×
VulnerabilityMultiplier
但是注意：
当前首版并不意味着四个区都必须大量使用。
其中易伤属于预留/后期机制。
________________________________________
十七、DMG3第一部分：通用增伤
通用增伤：
全部进入同一个加算池。
例如：
+20%
+30%
+15%
计算：
GenericMultiplier
=
1 + 0.20 + 0.30 + 0.15
=
1.65
最终：
×1.65
________________________________________
十八、什么属于通用增伤
原则：
只要不是明确依赖某个特殊BD条件的普通伤害提升，都优先进入通用增伤池。
例如：
全伤害
技能伤害
攻击伤害
某类普通伤害
其他普通成长
具体来源可以来自：
各养成系统
本文不规定具体养成系统名称。
________________________________________
十九、通用增伤为什么采用加算
因为这是基础成长区。
例如：
+50%
+50%
+50%
结果：
×2.5
而不是：
1.5 × 1.5 × 1.5
=
×3.375
这样可以控制普通成长的数值膨胀。
________________________________________
二十、DMG3第二部分：暴击乘区
暴击率与暴击伤害必须分开。
暴击率
负责：
决定是否暴击。
属于DMG2的判定。
暴击伤害
负责：
决定暴击之后的伤害倍率。
属于DMG3。
________________________________________
二十一、暴击伤害计算
假设基础暴击倍率：
1.5
如果拥有：
+50%暴击伤害
则：
CriticalMultiplier
=
2.0
非暴击：
CriticalMultiplier = 1.0
暴击：
CriticalMultiplier = 2.0
________________________________________
二十二、DMG3第三部分：BD特定增伤
这是本项目最重要的独立乘区。
只有明确属于：
某个特殊Build机制成立之后才产生的伤害放大
才进入BuildMultiplier。
例如：
目标处于某状态
    ↓
获得 ×1.3伤害
或者：
某个Build条件成立
    ↓
获得 ×1.5伤害
________________________________________
二十三、BD增伤采用独立乘算
假设同时获得：
BD效果A ×1.3
BD效果B ×1.4
BD效果C ×1.5
则：
BuildMultiplier
=
1.3 × 1.4 × 1.5
=
2.73
而不是：
1 + 0.3 + 0.4 + 0.5
=
2.2
目的就是：
让Build组件之间产生组合放大。
玩家获得多个互相配合的BD组件后，应该产生明显的“成型感”。
________________________________________
二十四、BD乘区必须严格控制
BD乘区虽然爽，但必须谨慎。
普通：
+20%伤害
不应该因为换了一个描述就变成：
×1.2
只有真正的：
特殊Build条件增伤
才可以进入BD乘区。
原则：
BD的爽感来自组件之间的组合，而不是所有伤害都做成乘算。
________________________________________
二十五、DMG3第四部分：易伤
易伤属于：
目标侧最终承伤放大。
如果目标处于易伤状态：
VulnerabilityMultiplier = 1.2
则：
FinalDamage × 1.2
易伤独立乘区。
________________________________________
二十六、易伤当前定位
易伤目前：
预留为中后期机制。
不应该在游戏前期大量出现。
原因是它属于全局放大器。
例如：
Generic ×1.8
Critical ×2.0
Build ×2.5
Vulnerability ×1.5
总倍率：
1.8 × 2 × 2.5 × 1.5
=
13.5
因此易伤必须谨慎控制。
________________________________________
二十七、DMG3最终公式
因此：
DMG3
=
GenericMultiplier
×
CriticalMultiplier
×
BuildMultiplier
×
VulnerabilityMultiplier
其中：
GenericMultiplier
=
1 + ΣGenericBonus
CriticalMultiplier
=
1
非暴击。
暴击时：
CriticalMultiplier
=
BaseCritDamage
+
BonusCritDamage
BD：
BuildMultiplier
=
Π(所有当前生效的BD倍率)
易伤：
VulnerabilityMultiplier
=
Π(所有当前生效的易伤倍率)
________________________________________
二十八、最终单次伤害公式
完整公式：
DMG1
=
AttackPower × SkillRate + SkillFlat
然后：
FinalDamage
=
DMG1
× DMG3
展开：
FinalDamage
=
(AttackPower × SkillRate + SkillFlat)
× GenericMultiplier
× CriticalMultiplier
× BuildMultiplier
× VulnerabilityMultiplier
但是：
这个公式只是最终数值公式。
真正的战斗执行仍然必须经过DMG2事件瀑布。
________________________________________
二十九、DMG2与DMG3的关系
这是整个架构最容易被错误理解的地方。
不能简单理解成：
DMG1
 ↓
DMG2
 ↓
DMG3
 ↓
结束
正确理解：
DMG1
 ↓
DMG2：战斗事件瀑布
 │
 ├─ Attack
 ├─ Target
 ├─ Hit
 ├─ Crit
 │
 └─ DamageEvent
       ↓
      DMG3
       ↓
   FinalDamage
       ↓
   Apply Damage
       ↓
      DMG2继续
       │
       ├─ OnDamage
       ├─ OnCrit
       ├─ Status
       ├─ Death
       ├─ OnKill
       └─ Chain Event
所以：
DMG3是DMG2中的“伤害计算节点”。
而不是完全独立的战斗阶段。
________________________________________
三十、DamageEvent
每一次实际伤害都应该生成一个标准：
DamageEvent
DamageEvent至少需要知道：
Attacker
Target
Skill
Source
DamageType
RawDamage
IsCritical
以及DMG3计算所需要的上下文。
________________________________________
三十一、所有伤害统一进入DamageEvent
例如：
普攻
Attack
 ↓
DamageEvent
技能
Skill
 ↓
Attack
 ↓
DamageEvent
BD触发额外攻击
BD Trigger
 ↓
New Attack Event
 ↓
DamageEvent
DOT
状态Tick
 ↓
DamageEvent
原则：
只要最终是“扣除目标HP的一笔伤害”，就应该能够表达为DamageEvent。
________________________________________
三十二、多段技能
多段攻击不要简单地把所有伤害合并成一次。
例如：
一次技能攻击3次。
应该产生：
DamageEvent 1
DamageEvent 2
DamageEvent 3
每个DamageEvent独立进入DMG3。
这样才能支持：
第1段暴击
第2段不暴击
第3段触发特殊效果
等战斗行为。
________________________________________
三十三、额外攻击
例如某个效果：
攻击后额外产生一把飞剑。
不能直接：
Damage × 2
应该：
原Attack Event
    ↓
DamageEvent
    ↓
触发条件成立
    ↓
生成新的Attack Event
    ↓
新的DamageEvent
新攻击重新走统一流程。
________________________________________
三十四、OnHit / OnCrit / OnKill
这些都是DMG2的事件节点。
OnHit
命中
 ↓
触发OnHit
OnCrit
暴击判定成功
 ↓
触发OnCrit
OnKill
Damage
 ↓
目标HP <= 0
 ↓
Death
 ↓
OnKill
这些事件可以生成新的：
Attack Event
Status Event
Effect Event
但不能绕过DamageSystem直接修改最终伤害。
________________________________________
三十五、链式战斗事件
未来BD可能形成：
攻击
 ↓
暴击
 ↓
额外飞剑
 ↓
击杀
 ↓
爆炸
 ↓
新的伤害
 ↓
再次触发某个效果
系统应该允许：
Event
 ↓
Trigger
 ↓
New Event
 ↓
New Event
因此战斗系统应该是：
事件驱动 + 可产生后续事件
而不是一个巨大Damage函数。
________________________________________
三十六、避免无限触发
链式事件必须能够识别：
Event Source
Event Depth
Trigger History
目的是避免：
A触发B
B触发A
A再触发B
B再触发A
...
当前开发阶段不需要复杂实现，但架构必须预留：
事件来源和触发链信息。
________________________________________
三十七、DPS计算
DPS不是伤害公式本身。
DPS由：
平均单次伤害
×
单位时间内伤害次数
得到。
即：
DPS
=
AverageDamage
×
HitFrequency
________________________________________
三十八、攻击频率
普攻：
HitFrequency
=
AttackSpeed
因此：
Basic DPS
=
AverageBasicDamage
×
AttackSpeed
________________________________________
三十九、技能频率
技能：
SkillFrequency
由技能CD以及：
CDR
共同决定。
不要用AttackSpeed控制技能释放。
不要用CDR控制普通攻击。
即：
AttackSpeed → Basic Attack Frequency
CDR → Skill Frequency
________________________________________
四十、暴击期望伤害
假设：
CritRate = C
CritMultiplier = M
则暴击期望倍率：
ExpectedCritMultiplier
=
(1-C) + C×M
例如：
CritRate = 50%
CritMultiplier = 2.0
则：
ExpectedCritMultiplier
=
0.5 + 0.5×2
=
1.5
理论平均伤害：
AverageDamage
=
NonCritDamage
×
ExpectedCritMultiplier
________________________________________
四十一、理论DPS
在没有特殊触发的简单情况下：
DPS
=
NonCritDamage
×
ExpectedCritMultiplier
×
AttackFrequency
技能则根据实际技能频率计算。
如果未来存在多个DamageEvent来源：
TotalDPS
=
Σ(
    EventAverageDamage
    ×
    EventFrequency
)
________________________________________
四十二、面板属性的职责
面板属性只负责提供：
当前角色最终能力值。
例如：
AttackPower
CritRate
CritDamage
AttackSpeed
CDR
各养成系统可以改变这些属性。
但是DamageSystem不需要知道：
“这个属性来自哪个养成系统。”
DamageSystem只读取最终结果。
________________________________________
四十三、各养成系统的职责
各养成系统只负责提供：
属性
Modifier
状态
技能参数
触发条件
最终统一进入战斗系统。
例如某个养成系统提供：
AttackPower +20
或者：
GenericDamage +20%
或者：
某条件成立时 BuildMultiplier ×1.3
DamageSystem不应该关心这个效果究竟来自哪个具体系统。
本文统一称：
各养成系统。
________________________________________
四十四、数据与逻辑必须分离
技能、属性、Modifier尽量采用数据驱动。
例如Skill数据：
Skill
{
    id
    type
    skill_rate
    skill_flat
    cooldown
    ...
}
DamageModifier：
DamageModifier
{
    type
    value
    condition
    source
}
战斗逻辑：
CombatSystem
DamageSystem
EventSystem
负责解释这些数据。
不要把具体数值硬编码在战斗代码里。
________________________________________
四十五、建议的系统边界
Claude Code实现时，可以保持以下职责：
CharacterStats
    ↓
提供最终面板属性

SkillSystem
    ↓
提供Skill数据

CombatSystem
    ↓
产生Attack Event
处理战斗事件瀑布

DamageSystem
    ↓
计算DMG1 / DMG3
产生最终Damage

EventSystem
    ↓
处理OnHit / OnCrit / OnKill / Chain

Target / Enemy
    ↓
维护HP与战斗状态
不要求当前阶段实现复杂的Entity体系，只要求职责边界清楚。
________________________________________
四十六、DamageSystem不能做什么
DamageSystem不要负责：
技能CD管理
攻击速度计时
敌人AI
角色移动
技能选择
事件触发逻辑
装备逻辑
养成逻辑
DamageSystem只负责：
“这一笔DamageEvent最终是多少。”
________________________________________
四十七、CombatSystem不能做什么
CombatSystem不要自己重新计算：
最终伤害
它应该：
产生事件
 ↓
调用DamageSystem
 ↓
拿到FinalDamage
 ↓
执行Apply Damage
 ↓
继续后续事件

× VulnerabilityMultiplier

=

=

五十二、Claude Code实现原则
Claude Code在实现时必须遵守以下规则：
规则1
不要把不同技能写成不同伤害公式。
所有Damage Event统一进入DamageSystem。
________________________________________
规则2
不要把DMG2实现成SkillMultiplier。
SkillRate属于DMG1。
DMG2是Combat Event Resolution。
________________________________________
规则3
不要把暴击判定和暴击倍率混在一起。
Crit判定 → DMG2
Crit倍率 → DMG3
________________________________________
规则4
不要把普通增伤做成乘算。
普通增伤：
1 + ΣBonus
________________________________________
规则5
BD特定增伤才进入独立乘区。
多个BD倍率：
A × B × C
________________________________________
规则6
不要自行增加新的伤害乘区。
当前固定：
Generic
Critical
Build
Vulnerability
如果未来出现新需求，必须先修改设计规则，再修改代码。
________________________________________
规则7
不要提前加入DEF、减伤、抗性等系统。
当前敌人的核心耐久轴就是：
HP
________________________________________
规则8
AttackSpeed和CDR不属于DamageMultiplier。
AttackSpeed → 普攻频率
CDR → 技能频率
________________________________________
规则9
额外攻击必须产生新的Attack Event。
不要简单修改原Damage。
________________________________________
规则10
所有链式效果必须通过事件系统产生后续事件。
不要在Damage函数内部不断增加特殊if/else。
________________________________________
五十三、当前版本最重要的四层概念
最终将整个系统压缩成四句话：
面板属性
我现在有多强？
DMG1
这一发本来能打多少？
DMG2
这一发攻击发生了什么？
DMG3
这一发最终被放大多少？
这四句话应该成为整个战斗系统的核心认知。
________________________________________

五十五、最终开发基线
《土豆修仙》当前战斗系统最终采用：
角色最终面板属性
        ↓
      Skill
        ↓
      DMG1
        ↓
  DMG2 战斗事件瀑布
        ↓
   Damage Event
        ↓
      DMG3
        ↓
   Final Damage
        ↓
    Apply HP
        ↓
 OnHit / OnCrit / OnKill
        ↓
   Chain Events
        ↓
  新的Attack Event
其中：
DMG1
=
AttackPower × SkillRate + SkillFlat
DMG3
=
Generic
× Critical
× Build
× Vulnerability
最终：
FinalDamage
=
(AttackPower × SkillRate + SkillFlat)
× Generic
× Critical
× Build
× Vulnerability
DMG2不参与一个固定的数学乘法公式。
DMG2的本质是：
战斗事件瀑布与结算顺序。
DMG3的本质是：
一笔DamageEvent的最终伤害倍率。
这套规则作为《土豆修仙》当前版本的 Combat System / Damage System 开发基线。任何后续战斗玩法、技能、效果或BD机制，都必须首先判断自己属于：
属性
DMG1
DMG2 Event
DMG3 Modifier
Attack Frequency
Skill Frequency
中的哪一层，再进行代码实现。
