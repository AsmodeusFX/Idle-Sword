《土豆修仙》战斗属性与 DamageModifier 开发规则 V1.0
1. 文档目的
本文用于明确《土豆修仙》的：
•	fightattr.csv 职责与边界
•	Static FightAttr 属性体系
•	属性投放规则
•	RuntimeBattleState 与 Static FightAttr 的关系
•	DMG1 / DMG2 / DMG3 对属性的读取方式
•	通用增伤属性的设计规则
•	BD 增伤、易伤以及条件型增伤的统一实现方式
•	后续新增战斗属性时的判断标准
本规则服务于数据驱动开发，并作为 Claude Code 实现战斗系统、属性系统和编辑器时的基础约束。
________________________________________
2. 核心定义
《土豆修仙》的战斗相关数值分为三类：
Static FightAttr
        ↓
RuntimeBattleState
        ↓
DamageModifier / Battle Event
三者职责必须严格区分。
________________________________________
3. Static FightAttr
3.1 定义
Static FightAttr 是：
角色进入战斗后，长期存在、可以被各种养成系统直接投放和累加的静态战斗属性。
这些属性统一由 fightattr.csv 定义。
例如：
atk_base
atk_percent
max_hp_base
max_hp_percent
crit_rate
crit_damage
attack_speed
skill_cdr
generic_damage
...
________________________________________
3.2 fightattr.csv 的核心用途
fightattr.csv 不只是给 CombatSystem 查数值。
它同时是：
所有属性投放系统的标准属性索引表。
因此以下系统如果需要给角色增加属性，都应该引用 fightattr.csv 中的 attr_id：
修为、法术、铸造等养成系统
例如：
attr_id = atk_base
value = 100
或者：
attr_id = atk_percent
value = 0.2
编辑器应直接读取 fightattr.csv 生成可选属性列表。
禁止各个系统自行维护一套重复的属性 ID。
________________________________________
4. FightAttr 与最终战斗属性
Static FightAttr 表示：
各个系统向角色投放了什么属性，以及这些属性累计形成的静态属性结果。
进入实际战斗后，再根据：
•	Static FightAttr
•	当前技能
•	Buff / Debuff
•	当前目标
•	当前战斗状态
•	条件
•	事件
计算得到 RuntimeBattleState。
因此：
Static FightAttr
≠
RuntimeBattleState
例如：
atk_base = 100
atk_percent = 50%
最终战斗攻击力：
ATK = 100 × (1 + 50%)
   = 150
战斗系统实际读取的是最终 ATK。
________________________________________
5. 已明确的 FightAttr
当前版本不要求一次性定义所有属性。
只将已经明确、且未来确定会被战斗系统使用的属性写入 fightattr.csv。
后续随着游戏功能增加，再逐步增加新的 FightAttr。
________________________________________
5.1 攻击力
攻击力至少拆分为：
atk_base
atk_percent
最终：
ATK
=
atk_base
×
(1 + atk_percent)
原因
不同系统可能分别投放：
+100 攻击力
+20% 攻击力
两者属于不同的属性投放维度，因此必须可以独立配置。
________________________________________
5.2 生命
生命值遵循与攻击力类似的思路。
至少预留：
max_hp_base
max_hp_percent
最终：
MaxHP
=
max_hp_base
×
(1 + max_hp_percent)
注意：
MaxHP
属于 Static FightAttr 计算出的最终战斗属性。
而：
HP
属于 RuntimeBattleState。
即：
MaxHP → FightAttr / 最终属性
HP    → RuntimeBattleState / 当前战斗状态
________________________________________
6. 暴击属性
当前明确包含：
crit_rate
crit_damage
6.1 crit_rate
表示暴击概率。
它由 DMG2 的：
Critical Resolution
读取。
例如：
crit_rate = 0.25
表示该次攻击有 25% 概率判定为暴击。
________________________________________
6.2 crit_damage
表示暴击后的最终暴击倍率。
默认值：
crit_damage = 1.5
后续所有增加暴击伤害的来源直接累加。
例如：
初始 = 1.5
天赋 +0.2
装备 +0.3
其他养成系统 +0.5
最终：
crit_damage = 2.5
DMG3：
CriticalMultiplier
=
crit_damage
注意：
crit_rate
负责“是否暴击”。
crit_damage
负责“暴击后是多少倍”。
两者职责不能混淆。
________________________________________
7. 攻击速度（普攻使用）
FightAttr：
attack_speed
攻击速度负责：
普通攻击发生的频率。
它不参与单次伤害公式。
即：
AttackSpeed
    ↓
Attack Interval
    ↓
Attack Event 发生频率
禁止：
AttackSpeed
    ↓
DMG1
也禁止：
AttackSpeed
    ↓
DMG3
除非未来明确设计某种“攻击速度转伤害”的特殊机制。
如果出现这种机制，应通过明确的属性转换或 Modifier 实现，而不是直接改变 AttackSpeed 本身的含义。
________________________________________
8. 技能冷却（法术使用）
FightAttr：
skill_cdr
负责技能释放频率。
它不参与单次技能伤害。
即：
skill_cdr
    ↓
Skill Cooldown
    ↓
Skill Release Frequency
禁止直接：
skill_cdr
    ↓
DMG1
或者：
skill_cdr
    ↓
DMG3
________________________________________
9. 通用增伤
通用增伤属于 FightAttr。
建议属性：
generic_damage
默认：
generic_damage = 0
其设计规则为：
所有属于“普通加算增伤区”的增伤属性，在 DMG3 第一乘区统一累加。
例如：
generic_damage = 20%
表示：
GenericMultiplier = 1.2
如果角色获得：
+20%
+30%
+15%
则：
generic_damage = 65%
最终：
GenericMultiplier = 1.65
________________________________________
10. 通用增伤的扩展规则
未来可以根据实际设计逐步增加更多“普通增伤属性”。
例如：
all_damage
skill_damage
basic_attack_damage
...
这些属性是否加入 FightAttr，需要根据实际游戏功能逐步确定。
如果某种增伤满足：
1.	是角色长期拥有的静态属性；
2.	可以被多个养成系统直接投放；
3.	不需要复杂条件才能判断；
4.	最终属于 DMG3 的普通加算增伤区；
则可以定义为 FightAttr。
例如：
all_damage
=
所有伤害 +X%

skill_damage
=
技能伤害 +X%

basic_attack_damage
=
普通攻击伤害 +X%
具体是否需要这些属性，不提前强制实现。
________________________________________
11. 通用增伤的统一规则
FightAttr 中的普通增伤默认采用：
Additive Damage Pool
即：
GenericMultiplier
=
1
+
Σ GenericDamageAttr
例如：
all_damage      +20%
skill_damage    +30%
basic_attack    +10%
如果当前 DamageEvent 是技能伤害，则：
GenericMultiplier
=
1 + 20% + 30%
=
1.5
如果当前 DamageEvent 是普通攻击，则：
GenericMultiplier
=
1 + 20% + 10%
=
1.3
因此：
属性是否生效，由 DamageEvent 的类型和属性定义决定。
FightAttr 本身只负责保存属性。
________________________________________
12. FightAttr 的重要边界
不能因为某个效果“看起来像增伤”，就把它加入 FightAttr。
判断标准：
应该进入 FightAttr
如果它是：
角色长期拥有，可以被各种系统直接投放的静态属性。
例如：
ATK
ATK%
MaxHP
MaxHP%
CritRate
CritDamage
AttackSpeed
SkillCDR
GenericDamage
...
不应该进入 FightAttr
如果它是：
只有满足某种条件时，针对某一笔 DamageEvent 才生效的效果。
例如：
对Boss伤害 ×1.5
对满血目标伤害 ×1.3
对燃烧目标伤害 ×1.5
生命低于30%时伤害 ×2
第5次攻击伤害 ×2
暴击后下一次攻击 ×1.5
...
这些统一属于：
DamageModifier
________________________________________
13. DamageModifier
13.1 定义
DamageModifier 是：
针对某一笔 DamageEvent，根据条件、状态或事件产生的动态伤害倍率或伤害修正。
它不属于角色永久属性。
________________________________________
13.2 DamageModifier 的主要来源
DamageModifier 可以由：
BD
技能
Buff
Debuff
被动效果
战斗事件
其他战斗逻辑
产生。
但是最终都必须进入统一的 Modifier 结构。
禁止每一个系统自行编写独立的伤害计算公式。
________________________________________
14. BD 增伤
BD 增伤属于 DMG3 的独立乘区。
定义：
BuildMultiplier
多个同时生效的 BD 增伤：
BuildMultiplier
=
Π(BuildModifiers)
例如：
BD效果A：×1.3
BD效果B：×1.4
BD效果C：×1.5
最终：
BuildMultiplier
=
1.3 × 1.4 × 1.5
=
2.73
________________________________________
15. BD 增伤不能直接写死在各个逻辑中
禁止出现大量类似：
if xxx:
    damage *= 1.5

if xxx:
    damage *= 1.3

if xxx:
    damage *= 2
尤其禁止不同技能、不同 BD 各自拥有一套独立伤害公式。
正确方式：
BD / Skill / Buff Logic
        ↓
生成 DamageModifier
        ↓
Modifier 注册到战斗上下文
        ↓
DamageEvent
        ↓
DMG3
        ↓
统一读取有效 Modifier
        ↓
BuildMultiplier
________________________________________
16. DamageModifier 的基本结构
第一版可以采用简单的数据结构：
DamageModifier
{
    source
    modifier_type
    multiplier
    condition
}
例如：
source = Talent_001

modifier_type = Build

multiplier = 1.5

condition =
    TargetHasStatus(Burn)
DMG3 结算时：
if condition == true
    Apply multiplier
________________________________________
17. 易伤
易伤与 BD 增伤在架构上属于同一种东西：
都是针对 DamageEvent 的动态倍率 Modifier。
区别只在于：
BDMultiplier
和：
VulnerabilityMultiplier
属于 DMG3 不同的乘区。
________________________________________
17.1 易伤公式
VulnerabilityMultiplier
=
Π(Active Vulnerability Modifiers)
例如目标当前存在：
易伤A ×1.2
易伤B ×1.3
则：
VulnerabilityMultiplier
=
1.2 × 1.3
=
1.56
________________________________________
18. BD 增伤与易伤的统一实现
最终 DMG3 可以保持：
DMG3
=
GenericMultiplier
×
CriticalMultiplier
×
BuildMultiplier
×
VulnerabilityMultiplier
其中：
GenericMultiplier
来自 FightAttr。
CriticalMultiplier
来自 FightAttr + 当前暴击结果。
BuildMultiplier
来自 DamageModifier。
VulnerabilityMultiplier
来自 DamageModifier / Target状态。
________________________________________
19. 完整伤害公式
最终：
DMG1
=
AttackPower × SkillRate + SkillFlat
然后 DMG2 负责整个战斗事件瀑布。
当进入 DamageEvent 后：
FinalDamage
=
DMG1
×
GenericMultiplier
×
CriticalMultiplier
×
BuildMultiplier
×
VulnerabilityMultiplier
其中：
GenericMultiplier
=
1 + Σ有效普通增伤 FightAttr
CriticalMultiplier
=
1
非暴击时。
CriticalMultiplier
=
crit_damage
暴击时。
BuildMultiplier
=
Π(所有当前有效 BD DamageModifier)
VulnerabilityMultiplier
=
Π(所有当前有效易伤 DamageModifier)
________________________________________
20. RuntimeBattleState
RuntimeBattleState 是战斗过程中实时存在的动态状态。
例如：
HP
当前Buff
当前Debuff
当前技能CD
当前攻击计时
当前目标
当前状态
当前战斗事件上下文
...
它不是 fightattr.csv。
例如：
max_hp = 1000
hp = 735
其中：
max_hp
来自 FightAttr 最终计算。
hp
属于 RuntimeBattleState。
________________________________________
21. FightAttr / Modifier / RuntimeBattleState 三者关系
统一理解为：
FightAttr
    ↓
我长期拥有多少属性

DamageModifier
    ↓
这一笔伤害在当前条件下获得什么额外修正

RuntimeBattleState
    ↓
我现在处于什么战斗状态
例如：
角色：
ATK = 150
CritRate = 30%
CritDamage = 200%
GenericDamage = 40%
这些属于 FightAttr。
战斗过程中：
目标处于燃烧
BD条件满足
目标处于易伤
产生：
BuildModifier ×1.5
VulnerabilityModifier ×1.3
这些属于 DamageModifier。
同时：
HP = 700 / 1000
SkillCD = 2.3s
CurrentTarget = Enemy_05
属于 RuntimeBattleState。
________________________________________
22. 后续新增属性的判断流程
以后新增任何战斗数值，Claude Code / 策划都按照以下顺序判断。
第一步：它是不是角色长期拥有的属性？
如果不是：
→ 不进入 FightAttr
→ 考虑 RuntimeBattleState / DamageModifier
如果是：
→ 进入下一步
第二步：它是否需要被各种系统直接投放？
如果是：
→ 定义 FightAttr
→ 加入 fightattr.csv
如果不是：
→ 考虑是否应该成为系统内部数据
第三步：它是加算属性还是独立乘区？
普通长期属性：
→ FightAttr
→ 按属性定义进行累加
特殊条件倍率：
→ DamageModifier
第四步：它是否需要判断当前攻击/目标/状态？
如果需要：
→ 优先考虑 DamageModifier
________________________________________
23. 禁止事项
禁止 1：各系统自己维护属性 ID
错误：
TalentSystem:
    talent_atk

EquipmentSystem:
    equip_attack

SkillSystem:
    skill_attack
正确：
fightattr.csv:
    atk_base
所有系统统一引用：
attr_id = atk_base
________________________________________
禁止 2：各系统自己计算最终伤害
禁止：
SkillA:
    damage = ...
    damage *= ...
SkillB:
    damage = ...
    damage *= ...
最终所有伤害都必须进入：
AttackEvent
    ↓
DMG1
    ↓
DMG2
    ↓
DamageEvent
    ↓
DMG3
________________________________________
禁止 3：把条件型增伤全部做成 FightAttr
不要不断增加：
boss_damage
burn_damage
low_hp_damage
full_hp_damage
first_hit_damage
fifth_hit_damage
...
如果其本质是：
满足某个条件才生效的倍率。
优先使用：
DamageModifier
________________________________________
禁止 4：直接修改已经计算出的最终伤害
不要让不同逻辑在 DMG3 外部：
final_damage *= 1.5
正确方式：
生成 Modifier
        ↓
进入统一 DMG3
这样可以保证伤害结算顺序、日志、调试和扩展的一致性。

crit_damage

25. 后续可以自然扩展的 FightAttr
随着游戏功能增加，可以逐步加入：
all_damage
skill_damage
basic_attack_damage

heal_bonus
shield_bonus

move_speed

projectile_count
projectile_speed
area_bonus
duration_bonus
...

但这些不是当前版本强制实现。
新增之前必须先判断：
这是角色长期拥有、可以被养成系统直接投放的静态属性吗？
如果是，则可以进入 FightAttr。
如果只是：
某个 BD 在某个条件下让某一笔伤害 ×X。
则应该进入 DamageModifier。

26. 最终架构原则
《土豆修仙》的战斗属性系统遵循以下原则：
fightattr.csv
    ↓
定义所有可投放 Static FightAttr
    ↓
各养成系统统一投放属性
    ↓
计算最终 FightAttr
    ↓
形成 RuntimeBattleState
    ↓
Attack Event
    ↓
DMG1
    ↓
DMG2 战斗事件瀑布
    ↓
DamageEvent
    ↓
读取 FightAttr
    +
读取有效 DamageModifier
    ↓
DMG3
    ↓
FinalDamage
核心职责：
FightAttr
=
“角色有什么长期战斗属性”

DamageModifier
=
“这一次伤害为什么获得特殊倍率”

RuntimeBattleState
=
“角色/目标现在处于什么状态”

DMG1
=
“这一发攻击原始能打多少”

DMG2
=
“这一发攻击在战斗中发生了什么”

DMG3
=
“这一笔 DamageEvent 最终被哪些倍率修正”
后续所有战斗数值设计，都必须优先遵守这套边界。
