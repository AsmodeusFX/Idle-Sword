# 《土豆修仙》核心成长系统设计规范 V0.1

## 0. 文档定位

本文用于定义《土豆修仙》核心成长系统的**设计边界、系统职责、资源关系、成长逻辑与实现原则**。

本文不是具体数值表，也不是具体内容配置表。

重点解决：

* 每个系统“负责什么”
* 每个系统“不负责什么”
* 各系统之间如何产生关系
* 各系统使用什么资源
* 资源如何解锁、获得、消耗
* Node 在整个成长体系中的职责
* BD 的主要来源是什么
* 如何避免系统之间功能重复、互相污染

---

# 1. 总体设计原则

《土豆修仙》的核心成长体系采用：

> **修行提供长期成长主线，法术提供技能内容，神通提供 BD，神识提供自动化与战斗逻辑。**

四个系统职责必须明确区分。

| 系统 | 核心问题                   | 主要产出            |
| -- | ---------------------- | --------------- |
| 修行 | “我现在修炼到了什么程度？”         | 境界、基础属性、系统解锁    |
| 法术 | “我会什么法术？”              | 法术库、法术等级、战斗技能   |
| 神通 | “我如何构筑自己的战斗体系？”        | BD机制、条件、强化、规则改变 |
| 神识 | “我能同时处理多少事情，以及战斗有多聪明？” | 自动化、战斗逻辑、操作效率   |

核心关系：

```text
                    修行
                     │
             ┌───────┼───────┐
             ↓       ↓       ↓
           法术     神通     神识
             │       │       │
             └───────┼───────┘
                     ↓
                  战斗表现
```

但是：

> **修行不是所有系统的上级技能树。**

它主要负责**解锁与长期成长阶段**。

例如：

* 修行到筑基 → 解锁新的法术内容
* 修行到金丹 → 解锁炼丹系统
* 修行到某个节点 → 解锁新的神通槽
* 修行到更高境界 → 神识系统开放新的能力

但解锁以后，系统应该尽量**独立运行**。

---

# 2. 资源体系总原则

四个系统采用**独立货币体系**。

不要使用一个“万能修仙点数”同时升级所有系统。

例如：

```text
修行
  ↓
修为

法术
  ↓
法术灵韵 / 法术真意

神通
  ↓
神通真意

神识
  ↓
神识精粹
```

具体货币名称可以后续统一命名，本文只定义职责。

## 2.1 货币基本规则

每个系统原则上：

> **一个主要成长货币 → 对应一个主要成长系统。**

例如：

```text
修为 → 修行
法术货币 → 法术学习/升级
神通货币 → 神通解锁/升级
神识货币 → 神识成长
```

避免：

```text
一个货币：
修行、法术、神通、神识全部使用
```

也避免：

```text
法术学习货币
法术升级货币
法术突破货币
法术重置货币
法术强化货币
……
```

初期不需要把一个系统拆成大量货币。

---

# 3. 货币解锁原则

一个非常重要的规则：

> **成长系统不是一开始就把所有货币全部掉出来。**

新的系统/货币应该通过**修行 Node 解锁**。

例如：

```text
炼气阶段
    ↓
修行 Node
    ↓
解锁法术系统
    ↓
怪物开始掉落「法术货币」
```

之后，修行 Node 可以继续强化该货币：

```text
解锁法术货币
    ↓
法术货币掉落 +20%
    ↓
法术货币掉落 +30%
    ↓
精英怪法术货币 +1
    ↓
Boss法术货币掉落提升
```

后期其他系统也可以参与强化：

```text
修行 Node
      ↓
法术货币掉落 +X%

神识
      ↓
自动拾取/掉落效率提升

某些其他成长系统
      ↓
法术货币获取效率提升
```

但必须遵循：

> **Node负责“开启/强化资源获取渠道”，其他系统负责“进一步提高效率”。**

这样能够形成很清晰的增量游戏资源循环。

---

# 4. Node 总体规范

Node 是《土豆修仙》的**长期成长载体**。

但不同系统的 Node 职责不同。

本文中最重要的是：

> **修行 Node 是整个游戏最主要的长期 Node 树。**

---

# 5. 修行系统

## 5.1 系统定位

系统名称固定为：

> **修行**

不要使用“修为系统”作为系统名称。

“修为”可以作为资源名称。

即：

```text
系统：修行

资源：修为

阶段：境界
```

玩家的成长体验是：

> **不断修行 → 积累修为 → 在修行道路上前进 → 突破境界 → 获得更高层次的能力。**

---

# 5.2 修行 Node 的结构

修行 Node 为：

> **横向无限拓展、纵向最多 5 行。**

整体阅读方向：

```text
左 → 右

┌──●──●────●──────●────●───→
│     │          │
├─────●────●─────●────●─────→
│          │
├──●──●────●────────●────────→
│
├────●────●──────●──────●───→
│
└──●────●────────●────●──────→
```

### 结构要求

* 横向：原则上不设固定长度限制
* 纵向：最多 5 行
* Node 通过连线形成可选择的成长路径
* 左侧为较早期内容
* 右侧为更后期内容
* 不要求每个 Node 都严格线性连接
* 允许分支、汇合、跨行连接

---

# 5.3 境界是修行树的核心锚点

修行树的主结构为：

```text
修行
 ↓
节点成长
 ↓
阶段性选择
 ↓
境界突破 Node
 ↓
进入下一境界
 ↓
新的修行区域
```

例如：

```text
炼气
  ↓
●──●──●
   ├──●
   └──●
      ↓
   【筑基突破】
      ↓
●──●──●
   ├──●
   └──●
      ↓
   【金丹突破】
```

境界突破 Node 是整个修行树的重要里程碑。

---

# 5.4 修行 Node 的主要类型

修行 Node 主要分为以下几类。

### A. 基础属性 Node

例如：

```text
攻击力 +10
生命 +50
暴击 +1%
攻击速度 +2%
```

属于最基础的数值成长。

---

### B. 资源获取 Node

用于强化已经解锁的系统货币。

例如：

```text
法术货币掉落 +10%

神通货币掉落 +10%

神识精粹掉落 +15%
```

注意：

> 如果系统尚未解锁，这类 Node 不应该提前出现大量无意义内容。

---

### C. 系统解锁 Node

例如：

```text
【法术】
解锁法术系统

【神通】
解锁神通系统

【神识】
解锁神识系统
```

解锁后，对应系统正式进入游戏循环。

---

### D. 功能解锁 Node

例如：

```text
解锁第2个神通槽
解锁神通升级
解锁神通类型
解锁新的自动化功能
```

---

### E. 境界突破 Node

这是最高优先级的特殊 Node。

例如：

```text
【筑基】

突破成功后：
- 基础属性大幅提升
- 解锁筑基阶段内容
- 获得筑基境界能力
- 外观发生变化
```

---

### F. 特殊永久选择 Node

可以存在，但必须非常克制。

例如：

```text
命格强化
┌──────────────┐
│ 神通槽结构强化 │
└──────────────┘
        ↓
命神通槽 / 身神通槽结构发生变化
```

这种 Node 可以制造长期 build 差异。

但：

> **修行 Node 的主要职责不是做 BD。**

BD 的主要职责仍然属于神通。

---

# 6. 境界设计规范

境界是修行系统的核心。

境界同时承担四个职责：

```text
① 数值成长阶段
② 内容解锁阶段
③ 系统成长阶段
④ 角色视觉进化阶段
```

---

## 6.1 境界必须产生明显的成长跃迁

例如：

```text
炼气 → 筑基
```

不能只是：

```text
攻击力 +10%
```

而应该是：

```text
基础成长提升
+
新的内容
+
新的能力
+
新的视觉表现
```

玩家应该明确感受到：

> “我突破了一个新的生命层次。”

---

# 6.2 每个境界拥有一个境界专属能力

每个大境界应该拥有一个与境界主题高度相关的**固有能力**。

它：

* 自动生效
* 不占神通槽
* 不作为玩家 build 选择
* 属于角色本身的境界能力

例如仅作为设计示例：

### 炼气

主题：

> 灵气循环、恢复、积蓄

能力可以偏向：

```text
战斗外恢复
灵气积累
持续战斗能力
```

### 筑基

主题：

> 肉身建立、基础稳固

可以偏向：

```text
概率触发额外攻击
概率重复施法
```

### 金丹

主题：

> 丹成、力量内聚

可以偏向：

```text
法术强化
技能循环
持续效果增强
```

### 元婴

主题：

> 第二生命 / 神魂外显

可以偏向：

```text
持续召唤
额外行动
分身/灵体
```

### 化神

主题：

> 神念与天地规则

可以偏向：

```text
自动化
规则改变
战斗逻辑强化
```

具体能力后续再做。

---

# 6.3 境界必须影响视觉

境界突破后：

> **同一个土豆妖持续成长，而不是每次换成一个完全不同的角色。**

视觉变化应该具有连续性。

例如：

```text
凡妖
↓
炼气
↓
筑基
↓
金丹
↓
元婴
↓
化神
```

逐渐出现：

* 芽
* 根
* 灵纹
* 妖丹
* 灵体
* 神魂
* 法相

但始终保留：

> **“这是一颗土豆”**

的核心识别。

---

# 7. 法术系统

## 7.1 系统定位

法术解决：

> **“玩家会哪些攻击/战斗手段？”**

法术是**战斗内容库**。

不是主要 BD 系统。

---

# 7.2 法术采用“永久学习”模式

推荐：

> **法术一旦学习，永久进入法术库。**

不设置：

```text
5个法术槽
玩家每次换5个
```

也不让玩家在每次境界突破时重新选择法术。

原因：

目前游戏已经存在：

* 修行路径
* 神通槽位
* 神通选择

如果法术也采用装备槽：

```text
修行选择
+
法术选择
+
神通选择
+
神通槽结构选择
```

会让游戏变得过于复杂。

---

# 7.3 法术拥有等级

法术不是“一次性解锁后就结束”。

结构：

```text
学习法术
    ↓
法术 Lv.1
    ↓
法术升级
    ↓
Lv.2
    ↓
Lv.3
    ↓
……
```

法术升级消耗：

> **独立的法术成长货币。**

---

# 7.4 法术自动释放

基础战斗状态下：

> **所有已经学习的法术都可以进入自动战斗循环。**

玩家不需要手动选择：

> “现在释放哪个法术？”

而是由系统根据：

* 冷却
* 目标
* 法术规则
* 神识提供的逻辑
* 神通提供的改变

自动执行。

---

# 7.5 法术应该拥有标签体系

法术可以拥有多个标签。

例如：

```text
御剑术
标签：
【剑法】
【单体】
【飞行物】

万剑诀
标签：
【剑法】
【AOE】
【多段】

血祭
标签：
【血法】
【消耗生命】
【强化】

雷法
标签：
【雷法】
【范围】
【控制】
```

标签的主要作用是：

> **让神通能够针对法术进行 BD 构筑。**

---

# 7.6 法术与境界的关系

境界决定法术的**层级和表现复杂度**。

并不是：

> 每一个境界必须有一整套独立法术。

而是：

```text
低境界
→ 基础法术

中境界
→ 范围 / 持续 / 连锁 / 附加效果

高境界
→ 规则变化 / 大型表现 / 特殊机制
```

这样能够避免：

```text
5种流派 × 10个境界 × 每个境界若干法术
```

造成巨量内容压力。

---

# 7.7 法术系统不负责核心 BD

例如：

```text
万剑诀
```

本身可以是：

```text
释放剑雨
```

但：

```text
万剑诀每击中一个敌人，下一次伤害+10%
```

这种机制更适合放在：

> **神通**

而不是法术本体。

这样：

> 法术负责“是什么技能”，神通负责“这个技能如何被构筑”。

---

# 8. 神通系统

## 8.1 系统定位

神通是：

> **《土豆修仙》的主要 BD 系统。**

这是四个系统中最应该承担“build”的系统。

核心问题：

> **“我准备怎么战斗？”**

---

# 8.2 三类神通

神通分为：

```text
命神通
身神通
术神通
```

职责明确区分。

---

## 8.2.1 命神通

定位：

> **核心 Build / 规则级机制**

命神通数量应该最谨慎。

典型效果：

```text
满足某条件后，整个 Build 发生变化

某类法术获得全新的运行方式

某个核心机制被激活

某个战斗规则发生变化
```

例如：

```text
【剑心通明】

当装备3个剑法相关神通时：
剑法伤害 ×1.5
```

或者：

```text
【血炼】

生命低于30%时：
血法进入强化状态
```

这种才属于命神通。

原则：

> **命神通决定“我是什么流派”。**

---

# 8.2.2 身神通

定位：

> **角色本身的强化与通用战斗机制。**

例如：

```text
攻击力 +20%

暴击率 +5%

受到伤害后获得护盾

生命低于50%时攻击速度提升

击杀敌人后恢复生命
```

身神通可以提供：

* 属性
* 生存
* 资源循环
* 通用触发
* 通用战斗逻辑

但不应该大量改变某个具体法术的核心行为。

---

# 8.2.3 术神通

定位：

> **强化法术以及法术体系。**

例如：

```text
所有剑法伤害 +30%

剑法有10%概率额外释放一次

雷法命中后产生连锁

血法伤害提高，但消耗更多生命

AOE法术范围 +20%
```

术神通是：

> 法术与 BD 之间的主要桥梁。

---

# 9. 神通槽位设计

这是本系统非常重要的一条规则。

## 9.1 神通槽不是境界自动全部开放

神通槽采用：

> **Node 永久解锁。**

例如：

```text
修行 Node
   ↓
【解锁神通槽】
   ↓
永久获得一个新的神通槽
```

这意味着：

> 玩家是在“修行道路”中逐步获得自己的神通容量。

而不是：

```text
到了筑基
系统自动给你5个槽
```

---

# 9.2 神通槽可以被永久改造

除了直接获得新槽之外：

> Node 可以将某个已有槽位转化为“自定义槽位”。

例如：

```text
普通身神通槽
      ↓
Node
      ↓
自定义神通槽
      ↓
可以装备：
身神通 OR 术神通
```

这样实际上提供了：

> **有限度的槽位结构自由度。**

---

# 9.3 自定义槽位的意义

例如原本：

```text
命 × 1
身 × 3
术 × 3
```

玩家通过 Node 获得：

```text
身槽 → 自定义槽
```

变成：

```text
命 × 1
身 × 2
自定义 × 1
术 × 3
```

这个自定义槽可以：

```text
身神通
OR
术神通
```

于是玩家可以产生：

```text
偏生存
```

或者：

```text
偏技能
```

的长期差异。

---

# 9.4 命神通必须谨慎开放

这是一个重要设计原则：

> **不要轻易把命神通槽变成自定义槽。**

原因是：

命神通承担的是：

> Build 核心规则。

如果玩家可以大量自由改变：

```text
命 ↔ 身 ↔ 术
```

会导致：

* 命神通过多
* BD核心机制泛滥
* Build边界消失
* 后期组合爆炸
* 平衡难度快速上升

因此：

```text
身 ↔ 术
```

可以通过 Node 有限开放。

而：

```text
命
```

属于高价值资源，应当非常谨慎。

---

# 10. 神通资源体系

神通拥有独立货币。

例如：

> 神通真意

来源：

```text
解锁神通系统
      ↓
怪物开始掉落神通真意
      ↓
修行 Node 提升掉落
      ↓
后续其他系统进一步提升获取效率
```

消耗：

```text
神通解锁
+
神通升级
```

---

# 10.1 神通本体应该有等级

神通不是只能：

```text
拥有 / 没有
```

而应该：

```text
神通 Lv.1
↓
Lv.2
↓
Lv.3
……
```

但是：

> **升级应该主要强化数值，而不是不断增加复杂规则。**

例如：

```text
Lv1：剑法伤害 +20%
Lv2：+30%
Lv3：+40%
```

而不是：

```text
Lv1：+20%

Lv2：+20%并增加额外攻击

Lv3：+20%并增加额外攻击+改变目标规则

Lv4：……
```

后者会让单个神通变成一个小系统。

---

# 11. BD 的核心结构

四个系统中：

> **神通 = BD核心**

法术提供：

> BD 的“技能素材”

修行提供：

> BD 的“成长空间和阶段解锁”

神识提供：

> BD 的“执行逻辑”

因此一个完整 BD 应该类似：

```text
法术：
万剑诀
天剑
剑影分光术

       ↓

术神通：
剑法伤害+
额外剑影
多段释放

       ↓

命神通：
剑心通明

       ↓

身神通：
暴击
攻击速度
击杀恢复

       ↓

神识：
优先释放万剑诀
Boss出现时保留爆发
```

最终形成：

> **玩家不是选择一个“职业”，而是在不断构筑自己的战斗逻辑。**

---

# 12. 神通与 Damage Multiplier 的关系

结合当前战斗公式，必须明确：

普通神通不要随意创造新的乘区。

例如：

```text
攻击力 +20%
剑法伤害 +30%
雷法伤害 +40%
```

都应该进入：

> General Damage Bonus

而真正的 Build 核心神通：

```text
当满足某条件：
剑法伤害 ×1.5
```

才允许进入：

> Build Multiplier

因此：

```text
普通神通
→ 数值成长

命神通 / 核心Build神通
→ Build规则
```

这是防止 BD 系统失控的重要边界。

# 13. 神识系统

## 13.1 系统定位

神识不是第四套攻击属性。

它解决：

> **“角色能同时理解、控制和自动处理多少事情？”**

这是一个非常适合增量游戏的系统。

---

# 13.2 神识资源

神识拥有独立资源。

例如：

> 神识精粹

来源：

```text
解锁神识
↓
怪物掉落
↓
修行 Node 提高掉落
↓
后期其他系统提高效率
```

---

# 13.3 神识主要强化三类能力

### ① 自动化

例如：

```text
自动拾取
自动分解
自动炼制
自动处理资源
```

具体功能以后扩展。

---

### ② 战斗逻辑

例如：

```text
优先攻击Boss

敌人 ≥ 5时优先使用AOE

Boss出现时保留高伤害法术

敌人低于20%时优先斩杀

优先维持某个Buff
```

这部分非常重要。

---

### ③ 多任务能力

例如：

```text
同时处理多个自动化任务

增加后台收益

提高多个系统同时运行的效率
```

---

# 13.4 神识不要变成纯属性系统

不推荐：

```text
神识 +10
→ 攻击力 +10
```

这样会导致：

> 神识变成第五种攻击属性。

应该尽量保持：

```text
神识
→ 更聪明
→ 更自动
→ 更高效
→ 更强的执行逻辑
```

# 14. 四个系统之间的资源关系

最终形成：

```text
                         【修行】
                            │
                    修为 + 修行Node
                            │
          ┌─────────────────┼─────────────────┐
          ↓                 ↓                 ↓
       解锁法术           解锁神通           解锁神识
          │                 │                 │
          ↓                 ↓                 ↓
      法术货币           神通货币           神识货币
          │                 │                 │
          ↓                 ↓                 ↓
       法术升级           神通升级           神识成长
          │                 │                 │

                       ↓             ↓
                     战斗          自动化
                       ↑             ↑
```

```text
  ↓
```

> **“解锁新资源 → 新系统成长 → 反过来加速资源获取 → 再推进修行”**

循环。

# 16. 最重要的系统边界原则

Claude Code 后续实现时必须遵守以下原则。

### 原则1：一个系统只有一个核心问题

```text
修行：我修到什么境界？

法术：我会什么？

神通：我怎么构筑？

神识：我怎么自动处理？
```

---

### 原则2：不要重复造系统

例如：

❌ 法术自己做一套 Build Tree

❌ 神通再做一套技能树

❌ 神识再做一套攻击强化树

❌ 修行再做一套完整 BD 系统

应该：

```text
修行 = 成长主线
法术 = 内容
神通 = BD
神识 = 自动化/逻辑
```

---

### 原则3：Node 是长期成长载体，不是所有系统的技能树

尤其是修行 Node。

它可以：

```text
加属性
解锁系统
解锁功能
强化资源获取
解锁神通槽
改变部分槽位结构
```

但不要让 Node 变成：

> “所有游戏内容最后都塞进 Node。”

---

### 原则4：货币必须有明确归属

```text
修为 → 修行

法术货币 → 法术

神通货币 → 神通

神识货币 → 神识
```

不要随意跨系统消耗。

---

### 原则5：系统之间可以互相增强，但不要互相吞并

正确：

```text
修行 Node
→ 法术货币掉落+20%

神识
→ 自动拾取法术货币

神通
→ 法术伤害+30%
```

不推荐：

```text
神通升级需要法术货币
法术升级需要神通货币
神识升级需要修为
修行Node又需要神识精粹
……
```

否则会形成复杂资源网。

# 17. 一个完整成长过程示例

假设玩家刚进入游戏。

### 阶段1：炼气

玩家：

```text
修行
↓
获得修为
↓
点修行Node
↓
获得基础属性
```

然后：

```text
Node
↓
解锁法术
↓
开始掉落法术货币
```

玩家学习第一个法术。

---

### 阶段2：继续修行

玩家继续：

```text
修行Node
↓
法术货币掉落提升
↓
法术升级
```

同时：

```text
Node
↓
解锁神通
↓
开始掉落神通货币
```

玩家获得：

```text
身神通
术神通
```

开始出现第一层 BD。

---

### 阶段3：筑基

玩家通过修行树：

```text
多个Node
↓
汇聚
↓
【筑基突破】
```

突破：

```text
基础属性提升
+
获得筑基能力
+
解锁新内容
+
角色外观变化
```

同时可以：

```text
Node
↓
解锁新的神通槽
```

玩家的 BD 容量提高。

---

### 阶段4：开始形成 Build

玩家拥有：

```text
法术：
剑法A
剑法B
雷法A
血法A
……
```

神通：

```text
命：
剑心类核心机制

身：
暴击
攻击速度

术：
剑法强化
额外释放
```

于是形成：

> 剑法 Build

另一个玩家可以：

```text
命：
血炼

身：
生命转伤害

术：
血法强化
```

形成：

> 血法 Build

两者拥有相同的法术库，但战斗表现完全不同。

# 18. 后续扩展必须遵守的原则

未来增加新系统时，不得直接破坏以上四系统边界。

例如未来增加：

* 炼器
* 炼丹
* 日月精华
* 其他修仙系统

新系统应该首先回答：

> **它解决哪个新的玩家问题？**

而不是：

> “这里还能塞什么成长属性？”

如果只是：

```text
攻击力 +10%
生命 +100
```

那么优先考虑是否应该进入现有系统，而不是新建系统。

## 最终架构一句话

我建议把整个核心成长体系最终牢牢收敛成这一句话：

> **修行决定“你走到了哪里”，法术决定“你会什么”，神通决定“你怎么打”，神识决定“你怎么自动打”。**

而**修行 Node**负责把整个游戏的长期成长空间串起来；**独立货币**负责把每个系统变成独立的增量循环；**神通槽 Node**则负责让玩家在不增加复杂操作负担的情况下，逐渐获得自己的 BD 结构。

这一版已经可以作为 Claude Code 的**架构约束文档**。下一阶段我们再单独做具体内容，不把“架构规范”和“数值/内容配置”混在一起。
