# 代码效率评估与优化记录

日期：2026-10-09。优化前代码基线：`ff4eca5`。

## 评估范围与结论

本轮检索了 `idle-sword/Core/`、`idle-sword/Features/`、`idle-sword/UI/`、`tests/` 与 `tools/` 的 C# 代码，排除缓存和构建产物；对固定步战斗、配置查询、养成属性、逐帧差分和存档克隆进行了定向阅读与验证。

主要可消除的成本来自重复配置扫描、重复解析天赋数值、热路径的 LINQ 闭包与数组快照，以及存活检测的嵌套扫描。已完成下表中的优化。伤害公式、乘区、配置数值、随机数调用次数与战斗结算顺序保持原口径。

| 路径 | 原开销 | 本轮处理与边界 |
| --- | --- | --- |
| `GameConfig.Row` / `GameSession.Level` | 每次线性扫描表或全部关卡 | 加载期建立 ID 索引；配置重载创建独立索引，缺失 ID 仍抛错 |
| `TalentBonus` | 每次扫描全部修行节点、解析每级数值 | 按效果缓存只读定义；等级每次从当前 `State` 读取，GM、购买、直接改状态立即生效 |
| `AttackRange` / 最近选敌 / 敌人状态查询 | 临时列表、闭包与查询对象 | 单次遍历；最近选敌同距离保留原列表顺序；其他目标排序规则不变 |
| 冷却衰减 | 每拍复制键数组，每个键重复查攻速/CDR | 复用键缓冲，两种频率在增益推进前各读取一次，增益法术仍不吃加速 |
| 效果推进 | 每拍复制全部效果 | 固定入口数量遍历；途中追加的派生效果下一拍才推进，末尾统一清理 |
| 自身增益与暴击缩冷却 | 数组快照、重复候选 LINQ | 复用独立增益与候选缓冲；候选顺序和随机抽签次数不变 |
| 灼烧推进 | 每拍过滤并复制敌人数组 | 敌人只在 Step 末尾移除，本段按原顺序直接遍历；仍在敌人行动之后结算 |
| `BattleView.TrackHits` / `CombatProbe.Measure` | 对每个旧 ID 再扫描全部敌人，O(n²) | 每帧/拍建立存活 ID 集合，线性差分；复用容器 |
| 召唤物位次 | 每帧创建两个集合与一个删除数组 | 复用集合和删除列表；新单位仍按效果插入顺序补最小空槽 |
| `SaveStore.Clone` | JSON 字符串中转 | 同一序列化规则改用 UTF-8 字节中转，深拷贝与存档格式保持一致 |

配置解析校验、养成购买、编辑器写盘、素材生成工具主要在启动或明确操作时执行，当前未发现需要优先改动的高频调用。磁盘原子存档、表头校验和缺失引用报错继续保留。

## 基准与复现

基准入口：`tests/PerformanceChecks.cs`，通过 `--performance` 单独运行，不代替功能自检。

```powershell
dotnet build -c Release tests/IdleSword.Checks.csproj
$env:DOTNET_TieredCompilation = '0'
dotnet tests/bin/Release/net10.0/IdleSword.Checks.dll idle-sword/Config/Tables --performance
Remove-Item Env:DOTNET_TieredCompilation
```

同机 .NET 10.0.12，Release，固定 seed=42。每个负载先预热，再测 5 次取中位数。关闭分层 JIT 是为了减少短测量中代码晋级与动态 PGO 的干扰；只影响上述测试进程，不修改游戏工程的运行设置。

战斗场景每次推进 2400 拍（步长 0.05 秒，共 120 模拟秒），包含 15 个法术，法术等级 8；普通循环设玩家无敌，沙盒额外摆 16/96 个高血定身靶。属性场景读取 10000 次攻击、气血与最大射程；克隆场景深拷贝 25 次含 96 个敌人的状态。准备会话与序列化轨迹不计入计时段。

优化前保留了同一份基准程序编译的旧代码二进制，优化后用相同配置和参数对照。以下为一次同机顺序测量；MB 按 1,000,000 字节计，分配量是当前线程累计托管分配，**不是常驻内存或显存**。

| 负载 | 耗时：优化前 → 后 | 分配：优化前 → 后 | 分配减少 |
| --- | --- | --- | --- |
| 普通关卡循环 | 78.793 → 15.646 ms | 25.63 → 7.24 MB | 71.8% |
| 沙盒 16 靶 | 26.031 → 7.906 ms | 24.30 → 5.94 MB | 75.6% |
| 沙盒 96 靶 | 55.728 → 20.211 ms | 84.40 → 10.94 MB | 87.0% |
| 属性读取 | 181.839 → 6.800 ms | 15.76 MB → 248 字节 | >99.99% |
| 存档深拷贝 | 11.727 → 8.775 ms | 8.88 → 3.95 MB | 55.5% |

这是受控 CPU/分配基准，不等同于实际游戏 FPS；默认分层 JIT 下也验证了分配与属性读取的改善，但绝对耗时会随预热、机器负载和 JIT 状态波动。Godot 的渲染提交、GPU 与真实磁盘保存延迟尚未单独采样。

## 行为验证

基准另跑逐拍轨迹：对玩家状态、敌人、效果、冷却、伤害账、移动状态及自身增益摘要序列化后累计 SHA-256。三个场景各 2400 拍的优化前后摘要完全相同：

| 场景 | SHA-256 |
| --- | --- |
| 普通循环 | `C728D37DADC477A0C0A5F5B5E6CE3F20AD1FEEA8F029E9A8F409C11C4A84DBE2` |
| 沙盒 16 靶 | `A91FF9EB15B5EDCCC5D478620CF8B54F0C0EF00F62E442B4E5CABC770E46D933` |
| 沙盒 96 靶 | `90D7893B06D734931BDF26FE82E0549687B4BCA882A4FBD49C656759F70A1A5E` |

这些摘要只适用于本轮配置，不应在以后调整数值时当成固定的玩法断言。

- 核心自检从 136 项扩为 139 项并通过；新增覆盖配置索引与重载隔离、天赋等级实时读取、最近选敌同距离顺序和更换战斗状态后的关卡读取。
- Godot 工程编译通过，零警告、零错误；`--smoke-test` 与 `--smoke-test --prologue` 均通过。表现优化未改布局。
- 基线已有的「前期数值锚点」跳过提示仍存在；战斗探针第 60 关模拟/模型比值仍为 2.798，与优化前一致。这些属于既有设计/模型问题，本轮未变更其判定。
- 普通冒烟退出时出现 2 个 ObjectDB 实例与 1 个资源的清理提示；项目已在 [阶段记录](../planning/phase_01.md) 中记录同类 .NET GC 时机噪声。本轮未将该提示算作运行时性能收益或新增泄漏结论。

## 后续测量优先级

1. 若实际长时间挂机仍有卡顿，先采集 Godot 帧耗时和 GC 时间，再决定是否调整范围命中的候选快照、多目标排序和绘制筛选。范围命中会改变敌人状态与裂隙合法性，不能直接把全部快照改为动态遍历。
2. 若真实磁盘保存造成长帧，单独测量序列化与原子替换耗时；异步化需要先设计提交顺序，确保首杀账本与奖励仍在同一次提交。
3. 本轮索引缓存依赖既有「配置加载后只读、编辑器修改后重载」约定；如未来引入热更新，应先补索引重建机制。
