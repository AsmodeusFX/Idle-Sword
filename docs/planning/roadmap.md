# 版本计划（Ver1.0 → Ver3.0）

> 状态：**Ver2.0 推进中**。本文件记录「要做成什么」，不记录「已经做了什么」——实现细节与逐轮取舍见 [phase_01.md](phase_01.md)。
> 规划中的 **Part 编号是思考流程，不是执行顺序**；真正开工时从哪一步切进去，见下面「Ver2.0 · 执行顺序」。

---

## Ver1.0（已完成）：还原原型

**目标**：把参考原型 [Zad Archery（ZAD）](../reference/zad_archery.md) 的核心功能还原出来，并把题材换成修仙。

- 主体是**战斗系统 + 技能系统**：解构 ZAD 的循环，把技能逐一替换成修仙概念的效果。
- 过程中建起了**编辑器、GM 命令、战斗统计**等开发设施（这些是为后面几版铺的路，不是 Ver1.0 本身的交付内容）。
- 结论：**已经够用了**——有战斗 + 技能，就可以边做边研究原型。

**这一版暴露的问题**（也就是 Ver2.0 的由头）：开始想不明白 ZAD 为什么非要那样设计；再往上一层问「如果我想跳出它的桎梏、形成自己的风格标签，这套框架该怎么抽象理解和重构」。

## Ver2.0（进行中）：把它变成我们自己的游戏

### 已完成的两步定形

1. **题材定形**：从题材出发重新问「它是修仙吗？是什么修仙？」——答案是**《土豆修仙》**，一种搞怪修仙。
2. **代入验证**：补了开场序章效果与前面几关的交互成长体验，回答「土豆修仙真的能让玩家代入吗？如果题材本身的效果不那么重要，前期的交互 + 成长能支撑一款增量放置游戏的用户引入吗？」——**当前答案是「基本可以」**（测试已过，数值体验后续还要细抠）。

### 接下来要做的五步

| Part | 内容 |
| --- | --- |
| **Part.1** | 明确**整个游戏所有养成系统的结构** |
| **Part.2** | 先巩固**战斗底盘**——把构成战斗价值的内容分门别类梳理好 |
| **Part.3** | 战斗底层与系统框架都清楚后，完成这些功能的**基础开发** |
| **Part.4** | **修为系统的编辑器功能**改造成人机分工（人出结构 + 意图，AI 出配置） |
| **Part.5** | 给各个功能**填上配置内容和数据**，让游戏流程基本运转起来 |

### 为什么 Part.2 要排在 Part.1 前面（思考，非执行序）

养成系统的一次流转可以抽象成三层：**如何获取资源 → 如何消耗资源 → 产出什么价值**。乐趣可以落在任一层（详见 [design_lens.md](../design/design_lens.md)），但玩家做决策的理由一定在第三层——**他觉得这个交互有价值**。增量游戏的资源获取天然与时间绑定、可操作空间有限，所以大部分乐趣会落在消耗侧（天赋树选方向这类），而**价值最终只能在战斗底盘里逐层释放出来**。

结论：**得先把战斗底盘梳理清楚，把有价值的内容分门别类，再分发给各个系统**。投放什么类型的价值，也决定了用什么手段投放——比如「御剑术的剑支数量」和「攻击力 +1」，在玩家层的吸引力完全不同，投放方式就该有差异。

这份「战斗价值分类」就是 [value_inventory.md](../design/value_inventory.md)。

### 执行顺序

**本轮（Ver2.0 开局）从 Part.4 切入**——先把节点编辑器这个工具搞定。理由：Part.1 往各系统分发价值时，用的正是 Part.4 产出的那条通道（「结构 + 意图 → 配置」）。工具先行，后面填配置才不靠手抠。

**进展（2026-10-07）**：编辑器这一路线已经落了两个——**节点编辑器**（修行星图的几何与拓扑 + 意图侧车）
与**关卡编辑器**（关卡的七个强度倍率、波次与首领、曲线视图、模型建议值、体检）。
两者都从 GM 面板的「编辑器与特殊功能入口 → 编辑器」进。**对编辑器角色的预设**（本轮拍板）：

> 编辑器**不是**为了手动配置整个游戏的数据，而是更依赖 AI 完成配置，人通过编辑器**检查、修正、指引方向**，
> 减少细节调整的沟通成本。所以每一屏的重心都放在"看得见"——曲线、建议值与偏差、实际数值预览、体检清单。

由此产生的一条**分工变更**：`level.csv` 的七个倍率列**从"工具生成"改成"编辑器为准"**，
`tools/BalanceCurve` 降级为"算建议、默认不写盘"。

落地形态见 [../design/](../design/) 与阶段记录；编辑器改造的人机分工口径写在编辑器代码顶部注释与本轮阶段记录里。

### 工程备注：留档的未来项

**角色综合战力统计 → 每关战力需求 → 一键造号**（2026-10-07 用户提出，**明确不在当前轮做**）。

要的是这样一条链：算出一个角色的**综合战力**（把修为 / 法术 / 武器 / 参悟 / 剑灵折成一个数），
再给出**每一关的战力需求**，于是测试时可以"一键造出对应战力的角色"，直接验"这一关的强度达标没有"。

它隐含两件**各自都是大工程**的东西，所以拆分记录：

1. **战力计算**——一个把各系统折算成单一标量的模型。它与 [balance_ttk.md](../design/balance_ttk.md)
   的 DPS 主轴是同一族问题，但口径不同（战力要涵盖生存与功能，不只是输出），得单独定。
2. **一键创建高级 / 定制账号**——往存档里灌一套指定练度的状态（修为等级 / 法术等级 / 武器 / 参悟）。
   注意它**不能绕过灵核账本**：存档校验里"灵核余额 ≤ 首杀数 + 调试发放量"那条是硬约束，
   所以要按"调试发放"那条既有通道记账（见 `GameSession` 的 GM 发放）。

> 关卡编辑器（`UI/LevelEditor.cs`）里的「试打这一关」是这条链的第一步——它已经能把人送到指定关卡，
> 缺的只是"把角色的练度也一起摆到我们要的位置"。
